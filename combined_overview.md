## Объединённый обзор Prompt Engineering  

### 1. Ключевая структура промпта  
| Блок | Что описывает | Пример (сокращённый) |
|------|---------------|----------------------|
| **Контекст / Persona** | «Кем» является модель, в какой области работает, какие ограничения соблюдает. | *Ты — senior TypeScript‑разработчик.* |
| **Задача / Instruction** | Одно конкретное действие, сформулированное глаголом. | *Сгенерируй, проанализируй, отрефактори.* |
| **Формат вывода** | Жёстко заданный контракт (JSON, Markdown‑таблица, список и т.п.). | `{"sentiment":"positive","score":9,"summary":"…"} ` |

> **Почему это важно:** без чёткого контекста и формата модель «угадывает» наиболее вероятный ответ, что приводит к «галлюцинациям» и невозможности автоматической обработки.

### 2. Общие техники улучшения промптов  

| Техника | Суть | Как применять |
|----------|------|---------------|
| **Few‑Shot / One‑Shot** | Добавление 1‑5 примеров `Input → Output`, чтобы показать желаемый паттерн. | Привести пару пар «вопрос‑ответ» в том же формате, что и требуемый результат. |
| **Chain‑of‑Thought (CoT)** | Просить модель рассуждать шаг за шагом. | Добавить фразу *«Реши задачу шаг за шагом»* или *«think step‑by‑step»*. |
| **Ask‑Before‑Answer** | Сначала уточняющие вопросы, потом ответ. | *«Спросите уточняющие детали, прежде чем генерировать ответ»*. |
| **Self‑Consistency** | Запуск одинакового промпта несколько раз, голосование/агрегация результатов. | Собирать 3‑5 ответов, выбирать наиболее частый или просить модель объединить их. |
| **Self‑Evaluation** | После получения результата попросить модель проверить себя. | *«Оцените, есть ли ошибки в полученном ответе»*. |
| **Constructive Criticism** | Запросить честную, неполитичную оценку кода/текста. | *«Критически оцените мой код, без смягчения»*. |
| **Emotional Prompting** | Добавление эмоционального «усилителя», чтобы повысить уверенность модели. | *«Это очень важно для моей карьеры; будь уверен в ответе»*. |
| **Prompt Chaining / RAG** | Делить большую задачу на последовательные шаги; при необходимости добавлять внешние документы. | 1) Выделить цитаты → 2) Сгенерировать ответ; 3) При необходимости добавить релевантные фрагменты из базы знаний. |
| **Image‑generation modifiers** | Указывать стиль, качество, тип съёмки и т.д. | *«photorealistic, 4K, cinematic lighting»*. |

### 3. Лучшие практики (объединённые из обеих статей)

1. **Конкретность** – формулируйте задачу однозначно, избегайте двусмысленностей.  
2. **Язык** – по‑возможности используйте английский (большая часть обучающих данных).  
3. **Ограничения** – явно указывайте лимиты (длина, количество примеров, время).  
4. **Формат вывода** – всегда задавайте структуру (JSON‑схема, таблица, нумерованный список).  
5. **Примеры** – держите их в едином стиле, количество ≈ 2‑5.  
6. **Пошаговость** – для сложных задач разбивайте на подпункты и просите «think step‑by‑step».  
7. **Уточнение** – если запрос неоднозначен, включайте «Ask questions for clarification before generating your answer».  
8. **Повторная проверка** – используйте Self‑Evaluation / Self‑Consistency для повышения надёжности.  
9. **Роли/Персоны** – задавайте детальное описание роли, чтобы модель «вжилась» в нужный контекст.  

### 4. Сокращённые уникальные детали  

| Тема | Кратко |
|------|--------|
| **История LLM** | LLM — большие языковые модели, обученные на терабайтах текста; масштаб → от млн до сотен млрд параметров. |
| **RAG (Retrieval‑Augmented Generation)** | Добавление внешних документов в контекст, полезно при ограниченном знании модели. |
| **Этика и обход ограничений** | Техники вроде CoT могут снижать отказ модели на чувствительные запросы; использовать с осторожностью. |
| **Генерация изображений** | Помимо текстовых техник, важны стилистические и технические модификаторы (качество, тип съёмки, настроение). |
| **Примеры ролей** | Учитель‑репетитор, главный редактор, senior‑Python‑разработчик – каждый с набором правил поведения. |
| **Методика разметки данных** | LLM могут помогать в NER, классификации, тональном анализе, но требуется пост‑проверка человеком. |

### 5. Быстрый чек‑лист для создания промпта  

```markdown
1. **Контекст**: «Ты — [роль], работаешь в [домен]».
2. **Задача**: «[Глагол] …», однозначно.
3. **Примеры** (если применимо):  
   Input: …  
   Output: …  
4. **Формат вывода**: «Ответ в JSON: { … }» или «Таблица Markdown».
5. **Доп. указания**:  
   - *think step‑by‑step*  
   - *ask clarifying questions before answering*  
   - *evaluate yourself*  
6. **(Опционально) RAG**: добавить релевантные документы.  
7. **(Опционально) Эмоциональный тон**: «Это критично для моего проекта».  
```

---  

**Итого:** обе статьи сходятся в том, что эффективный промпт — это чётко разделённый на контекст, задачу и формат запрос, подкреплённый примерами и/или пошаговыми инструкциями. Дополнительные техники (few‑shot, CoT, ask‑before‑answer, self‑consistency, RAG, эмоциональное усиление) позволяют повысить точность, надёжность и управляемость ответов как в текстовых, так и в визуальных задачах.
